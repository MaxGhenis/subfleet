# subfleet-guard: never-rules guard for subfleet codex lanes

## What and why

Agent lanes that crawl the whole disk saturate the SSD and beachball the Mac. On 2026-08-08, eight encoder-lane `find`/`rg` crawls of `~`, the mirrors, and `/tmp` ran in parallel and drove the load average to 47. On 2026-08-18 the e8 sol batch ran about 22 parallel `find / ...` and `find ~ ...` crawls and held load at 57 for hours. Both Claude Code and Codex now use one byte-identical `unscoped-search` region. It denies whole-tree `find`, `rg`, and recursive `grep` over the same broad roots in both lanes: `/`, `/*`, `/Users`, `~`, `$HOME`/`${HOME}`, `/Users/<user>`, the TheAxiomFoundation/RulesFoundation/PolicyEngine mirrors, `/tmp`, `/private/tmp`, and caches, including trailing-slash spellings. Depth-bounded and ordinarily scoped searches pass; the deliberately conservative syntactic cases retained by this regex guard are listed under Known false positives.

On 2026-08-19 the guard grew from that one rule to the full set: subfleet codex lanes now enforce all nine standing NEVER rules of `~/.claude/hooks/guard-never-rules.sh` (the Claude Code PreToolUse hook, the source of truth). Codex lanes run with the same host git config, gh auth, and network as Claude sessions, so every incident those rules encode — a lane force-pushing corpus main, squash-merging a signed-manifest repo, stashing in a shared-worktree clone, polling the Telegram bot, dumping the login keychain, rotating a trust root, branching from a stale local main, editing frozen HF upload destinations — is one tool call away in a lane too. Seven rules are ported as byte-for-byte copies of the Claude rule blocks; hf-dest is adapted to Codex's edit mechanics (`apply_patch` payloads and shell heredocs); unscoped-search is the shared region above.

## The rules

| `axiom-brief-regime` | `subfleet run … -C <under TheAxiomFoundation> -p <brief>` when the brief mentions rulespec/encoding but carries no `ENCODING REGIME` block | verbatim block (Max 2026-09-06: modules come only from `axiom-encode encode --apply`; a brief that says hand-author is a defect). |
| `hand-authored-rulespec` | `git commit` (incl. `git -C <dir> commit`) in a checkout whose origin is TheAxiomFoundation/rulespec-* when a staged rule YAML under `<cc>/(statutes|regulations|policies|legislation|programs)/` has no `.axiom/encoding-manifests/<mirror>.json` staged or tracked; `*.test.yaml` and `…/composed/…` are exempt | verbatim block; the CI guard is the second wall. |
| `corpus-squash` | `gh pr merge --squash`/`-s` when the repo (from `-R/--repo` or the payload cwd's origin) is TheAxiomFoundation/axiom-corpus or rulespec-* | verbatim block; identical semantics. |
| `corpus-push` | single-line `git push` of main/master (explicit refspec, `HEAD` on main, or bare push while on main) when the payload cwd's origin is axiom-corpus | verbatim block. The verbatim rule protects SINGLE-LINE pushes: a `git push` on line 2+ of a multi-line command, `git -C … push`, `git -c … push`, `--no-pager`, fully-qualified `refs/heads/main` refspecs and quoted refspecs are NOT caught (Claude-side follow-up). subfleet codex's own salvage push runs on the host, not through a tool call — untouched (and `-b main|master` is refused outright, see subfleet codex). |
| `stash-shared` | any `git … stash` in a repo whose payload cwd has >1 worktree (`git stash list` alone is exempt) | verbatim block. Lanes usually run INSIDE a worktree of a shared clone, so this is the common case — exactly the 7/17 near-miss. |
| `local-main` | `checkout -b`/`switch -c` with an explicit `main`/`master` start point, or a bare `-b <name>` while HEAD is on main/master — only when `refs/remotes/origin/main|master` exists | verbatim block. Legitimate lane setup passes: `git checkout -b x origin/main`, every `git worktree add` order, `-b` on a feature branch or detached HEAD, repos with no origin. This is the one rule a mid-flight lane is likely to meet; the deny message carries the fix. In upstream-style clones (pe-us main clone: org remote is `upstream`, origin is a stale fork) the advice names `origin/main` — use `upstream/main` there (follow-up). |
| `unscoped-search` | whole-tree find/rg/grep -r over broad roots | the shared region (byte-identical in both hooks). |
| `hf-dest` | adding upload-destination lines (`repo_id`, `huggingface.co/`, `hf://`, `upload_file`, `upload_folder`) to files resolving into `policyengine-uk-data` | ADAPTED: Codex has no Edit/Write tools — edits arrive as the freeform `apply_patch` tool (`tool_input.command` = raw patch text) or as a shell heredoc (`apply_patch <<'EOF' …`, tool_name Bash). The adapter mirrors Codex's own `StreamingPatchParser` over the patch: only ADDED (`+`) lines of in-scope file sections count; `*** Move to:` into uk-data counts; `*** Delete File:` does not. Path test, content regex, and block message are byte-identical to the Claude Edit branch. |

## Assessment notes (2026-08-19 port)

- Seven rules ported VERBATIM — no effective-cwd rewriting, no regex changes. The Claude hook stays the source of truth; every known gap/FP is documented below and pinned by a test, and rule improvements land Claude-side first (see Claude-side follow-ups).
- Heredoc bodies are judged as shell text, exactly as the Claude hook judges its own Bash heredocs (parity by design). To make that self-explanatory, a deny of a Bash command that carries `*** Begin Patch` appends: `[codex lane: this shell command carries an apply_patch body; the patch text was judged as shell text, as the Claude hook judges Bash heredocs. Use the apply_patch tool for file edits.]` — the Claude reason stays a byte-identical prefix. Observed sol lanes use the freeform apply_patch tool (169 calls, 0 heredocs in the sampled rollout), so the heredoc path is the minority.
- hf-dest bases: for tool `apply_patch`, relative patch paths resolve against the payload cwd. For the Bash heredoc form, the scan runs against the payload cwd AND every `cd`/`pushd` target found anywhere in the command — Codex intercepts only the two exact top-level heredoc forms, but non-intercepted forms STILL APPLY the patch (arg0 puts an `apply_patch`/`applypatch` alias of the codex binary on PATH; the standalone executable applies argv[1]-or-stdin against the shell's cwd), so `true; cd policyengine-uk-data && apply_patch <<'EOF'`, `pushd dir && apply_patch …`, and `apply_patch <<'EOF' … EOF && git add -A` all run for real and are all scanned. Leading `cd` option tokens and a `--` end-of-options terminator are skipped so `cd -- <dir>` / `cd -L <dir>` still yield the real operand; a leading `\cd` (alias-disabled but still a cd) is recognised and escaping backslashes are stripped from the operand (`cd policyengine-uk\-data`), while a shell-variable target (`cd "$VAR"`) or a glob target (`cd policyengine-uk-dat?`) cannot be resolved from the text and is a documented gap (below). Path matching is **case-insensitive** (added 2026-08-20): macOS APFS is case-insensitive, and Codex's lexical `PathUri::join` does NOT fold case, so `*** Add File: ../POLICYENGINE-UK-DATA/x` resolves to the protected repo when Codex applies it — the scan folds case so the alias is caught. Only bases that themselves contain `policyengine-uk-data` (case-folded; plus the payload cwd) are scanned — a base without the repo string can only scope a path that already contains it, so this changes no decision while keeping the scan a single pass regardless of how many `cd` targets the command has (measured: an 8000-`cd` / 650 KB command scans in ~0.6 s).
- Unicode-whitespace headers: the adapter trims each patch line the way Codex's parser does — Rust `str::trim()`/`trim_end()`, which strip the full Unicode White_Space set (NBSP U+00A0, ideographic U+3000, narrow-NBSP U+202F, NEL, U+2028/2029, …), not just the ASCII bytes POSIX `[:space:]` sees under `LC_ALL=C`. So a header hidden behind a no-break space (`<NBSP>*** Update File: …`) parses for the guard exactly as it applies for Codex; U+200B/U+FEFF (not White_Space) are left alone, matching Codex's rejection of such a patch.
- Rule order: the seven Bash blocks run first (Claude order: tg-getupdates, keychain-dump, trust-root, corpus-squash, corpus-push, stash-shared, local-main), then the shared unscoped-search region, then the fenced Bash-side hf-dest heredoc scan. `git push origin main && find ~ -name x` in a corpus clone denies `[corpus-push]`.

## Mechanism

- **Session-flags hook.** `subfleet codex` passes one extra `-c` override to `codex exec`: `hooks={PreToolUse=[{matcher="Bash|apply_patch",hooks=[{type="command",command="<abs path>/subfleet-guard-hook",timeout=60,statusMessage="never-rules guard"}]}],state={...}}`. Codex 0.144.0 reads hook config from the CLI override layer ("session flags") like any other config layer, so the hook is added for that run only. The guard writes nothing to the lane's `CODEX_HOME`, to `hooks.json`, or to any `config.toml`; hooks configured elsewhere keep working.
- **Matcher.** A matcher made only of `[A-Za-z0-9_|]` is an EXACT Codex matcher with `|` alternatives (`hooks/src/events/common.rs`), so `Bash|apply_patch` fires for the shell tools (`shell_command` and unified `exec_command` both arrive as tool_name `Bash` with `tool_input.command`) and for the freeform `apply_patch` edit tool (whose matcher aliases include `Write` and `Edit` — `core/src/tools/hook_names.rs`; its `tool_input.command` is the raw patch text).
- **Trust hash.** Codex runs a command hook only when its state says `enabled` and the trusted hash matches the hash it computes from the hook's normalized identity (`sha256:` + hex(sha256(compact JSON, keys sorted recursively, of `{event_name, matcher, hooks:[{type, command, timeout, async:false, statusMessage}]}`))). `subfleet-guard hash` reproduces that computation with `jq -cS` + `shasum`; `subfleet-guard override` embeds it in the same override under the hook's state key, with `enabled=true` so a stale `enabled=false` in a lane's `config.toml` cannot switch it off (session flags win field by field). The hash covers the handler IDENTITY (command string, timeout, matcher, status message) — NOT the hook file's content: a new file at the same path is trusted by lanes already running (their override is fixed at launch), so running lanes pick up a replaced hook file on their next tool call.
- **State key.** A session-flags PreToolUse hook in group 0, handler 0 has the key `/<session-flags>/config.toml:pre_tool_use:0:0` (`subfleet-guard key`).
- **Hook command.** Codex runs a command hook through a shell — the session's local shell with `-c` (`core/src/session/mod.rs::build_hooks_for_config` takes the turn environment's shell and calls `core/src/shell.rs::derive_exec_args(…, use_login_shell=false)`, e.g. `/bin/zsh -c "<command>"`), or `$SHELL -lc "<command>"` when no local environment shell is known (`hooks/src/engine/command_runner.rs::default_shell_command`) — so the command string is shell-interpreted; `subfleet-guard` single-quotes the hook path when it contains anything outside `[[:alnum:]@%+=:,./_-]` (the default path needs no quoting) and hashes the identical string. The hook sets its own `PATH` prefix, so which shell wraps it does not matter.
- **Timeout is fail-open.** The hook is armed with `timeout=60` (seconds). If it does not finish in time, `command_runner.rs` reports `hook timed out` as a run *error*, `hooks/src/events/pre_tool_use.rs::parse_completed` marks the run `Failed` and leaves `should_block=false`, so the tool call proceeds unguarded (same as any hook error). The hook normally costs about 100 ms (bash + a few jq/grep/awk/sed spawns; ~30 ms when the command has no searcher word) and cannot hang on stdin (Codex closes it after writing the payload); 60 s (Codex's own default is 600) means the guard still decides under the process-spawn stalls of a thrashing machine — the regime it exists for — while a wedged hook cannot hold a tool call for more than a minute. `TIMEOUT` lives in `bin/subfleet-guard`; the trust hash covers it, so changing it needs nothing else (the tests' pinned hash uses the test-only `--timeout 30`).
- **Preflight.** Before launching, `subfleet codex` runs `subfleet-guard preflight`, which starts `codex app-server` with the same override and asks `hooks/list` for the working directory. The hook must be listed with `enabled:true` and `trustStatus:"trusted"`; otherwise `subfleet codex` refuses to launch (exit 2, before its salvage trap is armed) instead of running unguarded. The probe runs in a **scratch `CODEX_HOME`** (a `mktemp -d` dir, removed afterwards) seeded with a copy of the lane's `config.toml` and `hooks.json` — the user-layer hook sources — so the check still sees the lane's `[hooks]`/`[features]` config (a lane whose `config.toml` says `features.hooks = false` fails preflight with `hook not listed`) while the lane home itself is never opened for writing. The probe passes `-c features.plugins=false` so app-server does not start its plugin-marketplace sync (which otherwise clones `github.com/openai/plugins` into `$CODEX_HOME/.tmp/`); the `hooks/list` result does not depend on network (verified under `sandbox-exec (deny network*)`) or auth. Success is cached per (codex version, lane home path, override, fingerprint of the seeded `config.toml`+`hooks.json`), so the check costs one app-server round trip (about a second) per lane per codex version per config edit. `CODEX_GUARD_PREFLIGHT_TIMEOUT` (default 60 s) bounds the wait for the `hooks/list` answer: an app-server that dies without answering fails the preflight immediately, and one that never answers is TERM/KILLed at the deadline (the npm `codex` launcher is a node process that forwards TERM to the native binary; direct children are signalled too), so a preflight cannot outlive the deadline by more than a few seconds.
- **No persistent config from the guard.** Everything the guard needs travels on the command line, and the probe home is scratch. Removing the guard block from `subfleet codex` removes the guard entirely. (Codex itself still maintains its own state under each lane home during `codex exec` — sqlite stores, sessions, project trust — exactly as it did before the guard existed.)
- **Why not `--dangerously-bypass-hook-trust`.** It also un-gates project `.codex/hooks.json` hooks in trusted repos: any repo a lane works in could then run arbitrary host commands. Pinning the trust hash gets the same effect for our one hook without that exposure.
- **Why not a PATH shim.** Codex runs shell commands through a login shell whose PATH is rebuilt by `/etc/zprofile` and `~/.zshrc`; a shim directory prepended by `subfleet codex` ends up behind the real `find` (`/usr/bin`) and `rg` (`/opt/homebrew/bin`). The hook runs before every shell tool call regardless of PATH.
- **Why not a prompt preamble.** The deny reason reaches the model in-band on the blocked call, with the exact scoping guidance, and `subfleet codex` keeps prompts verbatim.

## What a running lane sees after the cutover

Lanes launched before the 2026-08-19 files landed keep the override they were launched with (matcher `Bash`, status `unscoped-search guard`). Because the trust hash covers identity, not content, they get the new hook FILE on their next tool call: the seven Bash rules now judge their shell commands (stash-shared and local-main are the ones a mid-flight lane is likely to meet — both deny with the fix in the message), and the Bash-side hf-dest heredoc scan runs. But their freeform `apply_patch` calls never reach the hook (old matcher `Bash` only) until relaunch, so for them hf-dest exists only via the heredoc form. Lanes launched by the new subfleet codex get the full `Bash|apply_patch` matcher.

## Behavior seen by the agent

The model gets `Command blocked by PreToolUse hook: <reason>. Command: <the command or patch>` for both Bash and apply_patch (`core/src/hook_runtime.rs`; both payloads carry `command` in tool_input). Example reasons:

- unscoped-search: `[unscoped-search] Whole-tree find over a broad root (/, /Users, ~, ~/TheAxiomFoundation, ~/PolicyEngine, /tmp, caches) — 8 of these ran in parallel on 8/8 and drove load to 47, and ~22 sol-lane finds on 8/18 held load at 57 for hours, beachballing the Mac. Scope it: exact subdirectory, -maxdepth/--max-depth, 'git ls-files' inside a repo, 'axiom-locate' (engine|release|pypkg|corpus-file) for Axiom artifacts, or the interpreter for python package paths (python -c 'import x; print(x.__file__)'). Matched broad root: '/'.` The final token can also be `'~'`, `'~/PolicyEngine'`, `'$HOME'`, `'/Users (after cd)'`, or `'. (cwd /Users)'`. Depth-bounded searches, scoped subdirectories, `git ls-files`, and non-recursive `grep` pass untouched. `find .` is denied only when the payload cwd itself is a broad root.
- the seven ported rules: the Claude hook's messages byte-for-byte, e.g. `[stash-shared] NEVER git stash in shared-worktree repos — … 'git stash list' is allowed for recovery.` or `[local-main] Branch from origin/main, never local main — … Use: git fetch origin && git checkout -b <name> origin/main`.

If this edit is not a destination change, restructure it to avoid touching upload/repo_id lines; if it is, Max makes that change himself.` — identical for the freeform apply_patch payload and the heredoc form.
- any deny of a Bash command that carries `*** Begin Patch` additionally ends with ` [codex lane: this shell command carries an apply_patch body; the patch text was judged as shell text, as the Claude hook judges Bash heredocs. Use the apply_patch tool for file edits.]`.

## Known false positives (the seven ported rules + hf-dest)

Accepted, pinned as denies in `test_codex_guard_never_rules.py::test_documented_gaps_and_fps`; each deny message names the fix. All of these are properties of the verbatim Claude blocks (the source of truth), not of the port:

- **stash-shared** fires on prose and pathnames in shared-worktree cwds: `git commit -m "remove git stash usage from CI"`, `git log --grep stash`, `git diff -- src/stash.py`. It also judges `git -C <other> stash` against the payload cwd (deny in a shared cwd even when `<other>` is single-worktree — and the mirror gap below).
- **corpus-push** takes the bare-push path for `git push --tags origin` and does not check the remote name (`git push myfork main` denies); `cd ../corpus-wt && git push origin HEAD` is judged against the payload cwd (corpus main → deny).
- **local-main** denies a second `-b` after a correct one (`git checkout -b feat origin/main && git checkout -b feat2` while on main), and `cd <elsewhere> && git checkout -b x` / `git -C <elsewhere> checkout -b x` against the payload cwd's HEAD. In upstream-style clones the advice names `origin/main` even when that is a stale fork — use `upstream/main`.
- **tg-getupdates** fires on `grep -n "\.get_updates(" src/bot.py` (the pattern is indistinguishable from a call).
- **hf-dest** matches the Claude content regex on substrings: `+upload_files = []` and a docs line `+See https://huggingface.co/policyengine/policyengine-uk-data` in README.md deny (parity with the Claude Edit branch).
- **heredoc bodies**: a patch whose ADDED lines contain rule-shaped text is denied by the Bash rules (e.g. `+run git stash` in a shared-worktree cwd → `[stash-shared]`; `+Do not run: find ~ -name x` → `[unscoped-search]`), with the codex-lane suffix explaining why. Route such content through the apply_patch tool.

## Known false positives (unscoped-search)

Fixed on 2026-08-19 in the codex lane (the Claude lane still runs the OLD anywhere-in-the-command rule until the guard-portback `~/.claude` install lands — see Split landing state; until then the installed Claude hook still denies all three classes below): the old regex was replaced, so the codex hook's main position matcher no longer mistakes these three classes for search roots:

- a broad token owned by another command or data sink/source in an ordinary non-xargs compound, such as `ls -1 ~ | rg '^(e8-ops|.*ops.*)$'` (the real 00:09 and 00:35 false denials), `ls / && find . -name x`, an `-exec cp` destination, or a shell redirection target;
- a broad token inside an ordinary quoted pattern/program/message rather than an executable sub-script, such as `rg -n 'foo ~/PolicyEngine bar' src`, an awk `~` program, or `git commit -m "see ~/PolicyEngine"`;
- the unquoted pattern positional of `rg`/`grep`, such as `rg /tmp src` or `grep -r ~ src`.

The shared rule is quote-aware and position-aware for every root spelling. Three correctly scoped `rg` calls with ` / ` inside their patterns had also been denied on 2026-08-19; those now pass. How the rule reads a command:

- `${HOME}` is read as `$HOME`. Quoted strings are collapsed to a placeholder, except (a) a quoted string whose *whole* content is a root, which is unquoted so the position rules can judge it (`rg pat "/"` and `find "$HOME"/ …` are paths, `rg -n "/Users/" .` is a pattern), and (b) a sub-script — the argument of `bash -c`/`sh -lc`/`zsh -c`/`eval`/`xargs … sh -c` — that mentions a searcher, which stays visible (`bash -c "cd x && find '/' -name y"`); prose that merely mentions `find /` (`git commit -m "Add find / replace dialog"`) is collapsed.
- `find` counts a root anywhere in its own pipeline segment up to `-exec`/`-ok`; a `/` after a `|` or inside `-exec grep …` belongs to that command, which the rg/grep rules judge on their own. This deliberately does not parse predicates, so an exact root used as the value of `-newer`, `-path`, `-regex`, `-lname`, or `-samefile` also counts.
- `rg`/`grep` count a root in *path* position only — after the first non-option token (the pattern) of that `rg`/`grep`, not across `| ; &`. Value-taking options (`-g -t -A -B -C -m -M -j -d -D`, `--glob --type --context … --include --exclude --replace --sort …`) swallow their value. With `-e`/`-f`/`--regexp`/`--file`/`--files` in the segment every positional is a path (a root before or after the option counts; the option's own value never does), and other rg/grep segments of the pipeline are judged on their own.
- `xargs` invoking a searcher makes an unquoted root anywhere in the collapsed whole command count; a quoted root immediately feeding it (`echo "$HOME" | xargs rg pat`) also counts, while the documented quoted-pattern form (`git ls-files | xargs rg "/Users"`) passes. This intentionally conservative all-command check means an unrelated root can still fire in `ls /; git ls-files | xargs rg pat` or after the xargs pipeline in `find src -type f | xargs rg pat; stat /tmp`.
- `cd`/`pushd <root>` with any raw searcher word anywhere counts, including split-quoted shell scripts and regardless of command order or whether the search later names a child/file. Thus `cd /tmp && rg pat build.log`, `cd / && rg pat etc/hosts`, and `rg pat src; cd /tmp` deny. A literal broad root assigned by `for … in <root>` and fed to `find` also remains blocked. The rules are cumulative: `find "/" -name x | xargs rg pat` still denies.

So `rg "income / 12" src`, `grep -rn " / " src/`, `rg -e "/ " src`, `rg -e '/' src`, `rg -e / src`, `rg -n "/Users/" .`, `rg /Users src`, `rg -t py / src`, `echo / | rg x`, `ls / && find . -name x`, `find . -type f | grep -c /`, `find . -name "*.py" -exec grep -l "/" {} +`, `rg --files src | grep -v /`, `git ls-files | xargs rg "/Users"`, `git commit -m "Add find / replace dialog"` all pass, while `find / …`, `find "/" …`, `find /* …`, `find ~/ …`, `find "$HOME"/ …`, `find ${HOME}/PolicyEngine …`, `find ~/ …`, `rg pat /`, `rg pat "/"`, `rg 'pat' /Users`, `rg foo /tmp/`, `rg pat "$HOME/"`, `rg --files /`, `rg --files "~/"`, `rg / -e pat`, `rg "/" --files`, `rg -n "/" src -e foo`, `grep -r foo /`, `grep -r foo '/Users'`, `cd / && rg pat .`, `bash -c "cd / && find . -name x"`, `bash -c "cd x && find / -name y"`, `echo / | xargs rg pat` all deny. For every root-before-`-e`/`-f`/`--regexp`/`--file`/`--files` form, the deny message names the root—not the later option. Retained conservative residue, each with the token named in the deny message:

- `rg -r REPL / src`, `rg -E utf8 / src`, `rg -T py / src`, `rg --color never / src`: `-r`, `-E`, `-T` and `--color` are deliberately *not* treated as value-taking (in `grep` they are flags, and `grep -r foo /` must stay a crawl), so an unquoted `/` pattern right after them reads as a path — quote it or use the long form (`--replace`).
- `git ls-files | xargs rg /Users` (unquoted pattern after `xargs rg`) reads as a path — quote it.
- Any unquoted root elsewhere in a command containing `xargs … find|rg|grep` can fire because the mandated xargs rule examines the all-quotes-collapsed command, not shell data flow; the two compound examples above are representative.
- Any broad `cd`/`pushd` combined with a raw searcher word can fire regardless of ordering and even when the search names a single child/file, as in the three examples above.
- The cwd-dot rule intentionally judges the raw command against the payload cwd. From payload cwd `/` or `/Users`, `cd /etc && find . -name x` and `cd src && rg pat .` still deny even though the shell would change directory first. Quoted prose such as a commit message containing `rg pat .` can likewise fire in a broad payload cwd.
- Exact-root `find` predicate operands before `-exec`/`-ok`, such as `find src -newer /tmp -name x` or `find src -path /tmp`, are indistinguishable from start paths to this regex matcher and deny.
- Heredoc bodies are raw command text: writing a script or note that contains a blocked search can itself be denied. Put such content in a file-edit tool rather than a shell heredoc.

## Known gaps (whole guard)

Pinned as allows in `test_codex_guard_never_rules.py::test_documented_gaps_and_fps` where testable:

- **`workdir` argument.** Codex's shell tools accept a `workdir` parameter that is *not* in the hook payload, and the sampled sol rollout passed it on EVERY code-mode `exec_command` — so every cwd-dependent rule (stash-shared, local-main, corpus-squash/push repo identity, the unscoped cwd-dot rule, hf-dest bases) is judged against the lane's `-C` dir, not the tool call's effective directory. See the unscoped-search gap below for the mechanics.
- **`write_stdin`.** With unified exec on (the Codex macOS default), the model can open a PTY (`exec_command {cmd:"bash",tty:true}`) and then type anything via `write_stdin`, which emits NO PreToolUse payload at all (421 calls in one sampled sol rollout) — a full guard bypass. Mitigation: `SUBFLEET_CODEX_UNIFIED_EXEC=off` on the subfleet codex launch (adds `-c features.unified_exec=false`; shell_command only, no PTY sessions in the lane; source-verified against codex-rs 0.144.0, not yet live-verified). The default stays on — flipping it is Max's call.
- **MCP servers.** Tools served by MCP servers configured in a lane's config bypass the `Bash|apply_patch` matcher entirely.
- **cwd indirection.** `cd <dir> && …` / `git -C <dir> …` are judged against (stash-shared, local-main, corpus-squash) or not matched by (corpus-push needs `git push` adjacency) the payload cwd — so e.g. `cd ../shared-wt2 && git stash` from a single-worktree cwd passes, and `cd ../corpus && git push origin main` from a rulespec clone passes.
- **stash list exemption** is whole-command: `git stash list && git stash pop` passes.
- **corpus-push is single-line**: a `git push` on line 2+ of a multi-line command, `git -C . push`, `git -c k=v push`, `--no-pager push`, quoted refspecs (`'main'`), fully-qualified `HEAD:refs/heads/main`, and `-o ci.skip` shapes pass (the `-o` value is read as the remote).
- **corpus-squash**: `--squash=true`, combined short flags (`-sd`), `--repo=…` (no space), `GH_REPO=…` env form, and the `gh api …/merge -f merge_method=squash` API call pass; `--rebase` is allowed pending a .github#39 rule-6 decision.
- **trust-root**: `curl --request PATCH …`, `--field value=`, and `gh secret set AXIOM_*` pass.
- **tg-getupdates**: lowercase `/getupdates`, `run_polling()`/`start_polling()` wrappers, and `bot.getUpdates()` without a telegram-URL context pass.
- **keychain-dump**: a quoted `'-d'` flag passes, and naming any second non-login keychain masks a login dump in the same command.
- **local-main**: `-q -b`, `-B`, `switch --create`, `branch x && checkout x`, `worktree add … main`, `-b x HEAD` (while on main), and quoted `'main'` start points pass.
- **hf-dest**: path-substring identity — a worktree or symlink whose path lacks `policyengine-uk-data` (e.g. `~/PolicyEngine/_worktrees/uk-data-f1/…`) is invisible to BOTH hooks; a heredoc `cd` to a shell-variable target (`UK=policyengine-uk-data; cd "$UK" && apply_patch <<'EOF'`) is not resolved (the base derivation reads the literal `$UK`, not its value), nor is a glob target (`cd policyengine-uk-dat? && apply_patch …`); a heredoc body that assembles a forbidden token from shell-expanded pieces (`K=repo"_"id; apply_patch <<PATCH … +$K=evil …`) is scanned as the literal `+$K=evil`, which the shell only expands at apply time; `apply_patch < file`, `apply_patch "$(cat p)"`, `cat p | apply_patch` carry no patch text in the payload; shell writes (`sed -i`, `cat >`, `python - <<PY`, `git apply`, `patch`) and direct uploads (`hf upload`, `huggingface-cli upload`, `python -c '…upload_file(…)'`) reach the forbidden OUTCOME without an apply_patch edit; an `*** Environment ID:` line selecting a non-turn environment (multi-env sessions, not lanes) resolves elsewhere. (Case-aliased spellings on macOS — `POLICYENGINE-UK-DATA` — and `\cd`/`cd uk\-data` backslash forms ARE caught since 2026-08-20; the freeform-tool case bypass was found by the sol cross-family adjudication.)
- **Exposure assumptions.** How much trust-root/corpus-*/hf-dest are worth in a given lane depends on whether that lane has network and gh/HF credentials — `sandbox_workspace_write.network_access`, `mcp_servers`, and the shell env policy in the lane's config decide that, not the hook.

## Known gaps (unscoped-search)

- **`workdir` argument mechanics.** `shell_command.rs` builds `tool_input = {command}` only; the payload `cwd` is the turn's working directory. `{"command":"find . -name x","workdir":"~"}` therefore passes the cwd rule and cannot be seen by any hook. Unfixable in-hook; the only mitigation is the model's own discipline (the deny message it receives on the direct forms).
- **Odd root spellings and indirection.** `find // -name x`, `find /. -name x`, `find ~/* -name x`, `find /*/ -name x`, `find $HOME/* -name x`, brace expansion, general variable assignment (`d=/; find "$d"`), `cd .. && find .` from a child of a broad root, `find $PWD` in a broad cwd, and bare `cd && find .` are allowed. A direct `for d in <literal-broad-root>; do find "$d" …; done` is blocked, but arbitrary shell data flow is not parsed. `FIND / -name x` is allowed because matching is case-sensitive. A bare `rg pattern` with no path argument in a broad cwd is allowed. Any depth value disarms the rule (`find /Users -maxdepth 999`; ripgrep's short `-d N` is not recognised as the escape). Backslash-newline continuations are joined before judging since 2026-08-19; an even run of trailing backslashes retains the real command-separating newline.
- **Searcher not preceded by a delimiter.** `/usr/bin/find / -name x`, `$(which find) / -name x`, `bash -c 'find / -name x'` / `eval "find / -name x"` (searcher right after the opening quote), backtick substitution (`` echo `find / -name x` ``), `\find / -name x`, `egrep`/`ggrep -r pat /` are allowed: the searcher-detection regex needs whitespace, `;`, `&`, `|` or `(` before `find`/`rg`/`grep`.
- **Other crawlers.** `fd`, `ag`, `ack`, `locate`, `mdfind`, `tree /`, `du -a /`, `ls -R /` are not searchers in either hook (`fd`/`ag` are not installed here; `mdfind` uses the Spotlight index, cheap).
- (`cd ~ && find . -name x` is denied by both hooks — not a gap.)

## After a Codex upgrade

The preflight cache key includes the codex version, so the first `subfleet codex` on a new codex re-verifies against the real `hooks/list`. If the upgrade changed the hash scheme, the key format, or the hook config shape, `subfleet codex` prints `preflight: FAILED — hook listed but enabled=... trustStatus=modified currentHash=sha256:... expected=sha256:...` (or `hook not listed under key ...`, or `'codex app-server' exited without answering hooks/list` if it rejects the override at startup) and exits 2 with `guard preflight FAILED (see preflight output above); refusing to launch`. Fix: update `compute_hash`/`KEY` in `bin/subfleet-guard` to the new scheme (verify with `codex app-server` + `hooks/list`), re-pin the tests. Until then `SUBFLEET_CODEX_GUARD=off` bypasses per run.
